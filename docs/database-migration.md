# Database Migration Strategy

PostgreSQL + SQLAlchemy + Alembic/Flask-Migrate

Database schema changes are committed as migrations. A developer should never
edit a shared database by hand and expect everyone else to reproduce the change.

## Current baseline

The repository has two bootstrap paths:

1. `sql/sql-schema.sql` is mounted as a PostgreSQL init script for a fresh
   Docker volume.
2. `be/migrations/` contains the Flask-Migrate history used for future changes.

The migration history is:

```text
0001_baseline_schema       All tables that predate Flask-Migrate
0002_add_student_gpa       Optional student GPA table
0003_student_id_unique     Converts the legacy student_id index to a constraint
                         so autogenerate stays clean
```

The baseline migration uses `IF NOT EXISTS` on tables and indexes, and
`CREATE OR REPLACE`/`DROP IF EXISTS` on functions and triggers. This means both
of these work without a manual `stamp`:

```bash
# Database already initialized by sql/sql-schema.sql
flask --app run.py db upgrade

# Completely empty database
flask --app run.py db upgrade
```

`flask --app run.py db check` should report `No new upgrade operations
detected` after an upgrade.

Every model is imported in `be/app/models/__init__.py`. This matters because
`skills`, `student_skills`, and `student_gpa` previously had no ORM models, so
autogenerate would have proposed dropping them.

## Change workflow

```text
Developer changes model
        ↓
Create migration
        ↓
Review the migration
        ↓
Commit migration
        ↓
Other developers pull
        ↓
Run migration
        ↓
Their database gets updated
```

Commands, from `be/` with the virtual environment active:

```bash
flask --app run.py db migrate -m "add project submissions"
flask --app run.py db upgrade
flask --app run.py db check
```

Always review an autogenerated migration before committing it. In particular,
check that Alembic is not dropping tables or columns that exist only because a
model was not imported.

## Rules

- Migration files belong in Git.
- Actual database data does not belong in Git.
- Do not use `db create` or `db.drop_all()` as a substitute for migrations.
- Do not manually edit a database that other developers share.
- Back up data before running a baseline `downgrade`; it drops tables.
- Keep `sql/sql-schema.sql` in sync with the migration history for fresh
  container initialization.
